# RFC: Snapshot-Based Migration

**Status:** Draft
**Author:** Matt Kerian
**Date:** 2026-02-14
**Depends on:** `rfc-schema.md`, `rfc-storage.md`

## Summary

Pluto computes migrations automatically by diffing the current source code against a snapshot of the previously deployed state. No version numbers. No migration files. No manual DDL. The source code is the desired state; the snapshot is the current state; the compiler computes the transition.

## Motivation

Every migration system today has the same problem: **version numbers are bookkeeping that humans maintain and computers should compute.**

Rails migrations: `20240115_add_email_to_users.rb` — a manually numbered file that runs once and is never touched again. If two developers create migration 47, you get a conflict. If a migration fails halfway, the database is in an unknown state. If you want to know the current schema, you have to replay all migrations.

Flyway, Alembic, Liquibase: same pattern. Ordered files, manual numbering (or timestamps), applied sequentially. The migration history is part of the source code, growing monotonically forever.

Pluto takes a different approach: **source code = desired state**. The compiler sees the current schema declarations (desired), loads the snapshot from the last deployment (current), computes the structural diff, and generates the migration automatically. No version numbers. No migration files in the repo. No ordering conflicts.

## Design

### Core Concepts

**Source code** — The current state of all schema and storage declarations. This is what the programmer writes and edits. It represents the desired state of the system.

**Snapshot** — A build artifact that captures the state of all schemas and storage at the time of deployment. Created by the compiler, stored alongside the deployment. Not source code — not checked into the repo.

**Diff** — The structural difference between the snapshot and the current source. Computed by the compiler. Describes what changed: added fields, removed fields, type changes, new storage, removed storage.

**Migration plan** — The ordered set of operations that transitions the system from the snapshot state to the source state. Generated by the compiler from the diff and `from` clauses. Includes SQL DDL, data transformations, and deployment ordering.

### Workflow

```
1. Developer writes/edits schema and storage declarations
2. Compile: plutoc build --snapshot deployed.snapshot
3. Compiler loads snapshot, diffs against current source
4. Compiler generates migration plan
5. Developer reviews migration plan
6. Deploy: migration plan executes, new snapshot is created
```

Step 2-4 happen at compile time. The migration plan is output as a build artifact, not executed automatically. The developer reviews it before deploying.

### Snapshots

A snapshot captures:
- All schema declarations (names, fields, types, conditional fields, invariants)
- All storage declarations (names, kinds, schema bindings, indexes)
- All enum declarations (names, variants)
- Schema relationships (spreads, trait impls)

Snapshots are **build artifacts**, not source code:
- Created by the compiler during a deployment
- Stored alongside the deployment (in a deployment registry, S3, etc.)
- Referenced by subsequent compilations via `--snapshot <path>`
- One snapshot per deployment — represents the exact state at that point

**Fresh deployment** (no snapshot): No migration needed. The compiler generates CREATE statements for everything. This is the common case for new projects and new environments.

### Structural Diff

The compiler computes a structural diff between the snapshot and current source:

| Change | Diff Entry |
|--------|-----------|
| New schema | `Added(SchemaName)` |
| Removed schema | `Removed(SchemaName)` |
| New field | `FieldAdded(SchemaName, FieldName, Type)` |
| Removed field | `FieldRemoved(SchemaName, FieldName, Type)` |
| Type changed | `FieldTypeChanged(SchemaName, FieldName, OldType, NewType)` |
| Field renamed | Detected via `from` clause: `FieldRenamed(SchemaName, OldName, NewName)` |
| New storage | `StorageAdded(StorageName)` |
| Removed storage | `StorageRemoved(StorageName)` |
| Index added | `IndexAdded(StorageName, Fields)` |
| Index removed | `IndexRemoved(StorageName, Fields)` |
| New enum variant | `VariantAdded(EnumName, VariantName)` |
| Removed enum variant | `VariantRemoved(EnumName, VariantName)` |
| Conditional field added | `ConditionalFieldAdded(SchemaName, FieldName, Condition)` |
| Conditional field removed | `ConditionalFieldRemoved(SchemaName, FieldName, Condition)` |

### `from` Clauses: Structural Migration Hints

`from` clauses on schema fields tell the compiler how to transform data when the shape changes:

```
schema Order {
    // Renamed: "email" -> "customer_email"
    customer_email: string from email: string => email

    // Type changed: float dollars -> int cents
    total_cents: int from total: float => int(total * 100.0)

    // Split: "full_name" -> "first_name" + "last_name"
    first_name: string from full_name: string => split(full_name, " ")[0]
    last_name: string from full_name: string => split(full_name, " ")[1]

    // New field with computed default
    created_at: int from => timestamp()
}
```

**How `from` clauses work:**

1. The compiler diffs the snapshot against the current source
2. For each new or changed field, it looks for a matching `from` clause
3. A `from` clause matches if the snapshot has a field with the specified name and type
4. The `from` expression is used to generate the data transformation

**`from` with no source field:**

```
total_cents: int from => 0
```

This provides a default value for a new field with no corresponding old field. Used when adding a required field to an existing schema.

**Multiple `from` clauses:**

A field can have multiple `from` clauses for handling different possible old shapes:

```
schema Order {
    total_cents: int
        from total: float => int(total * 100.0)
        from total_dollars: float => int(total_dollars * 100.0)
        from price: int => price
}
```

The compiler tries each in order, using the first one whose source field matches the snapshot.

**`from` expressions must be pure:**

`from` expressions follow the same purity rules as schema functions — no DI, no I/O, no side effects. They run at migration time, not at runtime.

### Migration Plan Generation

The compiler generates a migration plan from the diff:

```
Migration Plan (snapshot: deploy-2026-02-10 -> current source)

1. ALTER TABLE orders ADD COLUMN customer_email TEXT;
2. UPDATE orders SET customer_email = email;
3. ALTER TABLE orders DROP COLUMN email;
4. ALTER TABLE orders ADD COLUMN total_cents INTEGER;
5. UPDATE orders SET total_cents = CAST(total * 100 AS INTEGER);
6. ALTER TABLE orders DROP COLUMN total;
7. CREATE INDEX idx_orders_customer_email ON orders (customer_email);
```

For `Table<T>` storage, the plan generates SQL DDL. For other storage kinds, it generates appropriate backend-specific operations.

### Migration Safety Rules

The compiler applies safety rules to the diff (see `rfc-evolution-rules.md`):

| Change | Default Rule |
|--------|-------------|
| Add required field without `from` clause | **Error** — data loss potential |
| Remove field | **Warning** — data loss |
| Change field type without `from` clause | **Error** — no transformation specified |
| Remove storage | **Error** — requires explicit confirmation |
| Remove enum variant | **Error** — existing data may reference it |
| Add enum variant | **OK** — backward compatible |
| Add optional field | **OK** — defaults to `none` |
| Add index | **OK** — non-destructive |
| Remove index | **Warning** — performance impact |

### Two-Phase Migration for Breaking Changes

Some changes can't be done atomically — the old code must work with the new schema during rollout. The compiler detects these and generates a two-phase plan:

**Phase 1: Expand** — Add new columns/fields alongside old ones. Both old and new code work.

**Phase 2: Contract** — Remove old columns/fields. Only new code runs.

Example: Renaming `email` to `customer_email`:

```
Phase 1 (deploy with old + new code running):
  ALTER TABLE orders ADD COLUMN customer_email TEXT;
  UPDATE orders SET customer_email = email;
  -- Both columns exist; old code reads "email", new code reads "customer_email"

Phase 2 (after all instances run new code):
  ALTER TABLE orders DROP COLUMN email;
```

The compiler determines whether a migration is single-phase (safe) or two-phase (breaking) based on the diff:
- **Single-phase:** Adding fields, adding indexes, adding enum variants
- **Two-phase:** Renaming fields, changing types, removing fields

### Deployment Ordering

When a compilation unit contains multiple services and storage declarations, the compiler generates a deployment order:

```
Deployment Order:
  1. Run storage migrations (SQL DDL)
  2. Deploy Service A (reads from migrated storage)
  3. Deploy Service B (depends on Service A)
  4. Run Phase 2 cleanup (drop old columns)
```

The ordering is derived from:
- Storage dependencies (migrate before services that use the storage)
- Service dependencies (DI graph determines service startup order)
- Two-phase boundaries (cleanup runs after all services are on new code)

### No Version Numbers

Notably absent from this design: version numbers, migration sequence numbers, timestamps on migrations, migration IDs, or any form of ordering metadata.

**Why this works:**
- Snapshots capture the full state, not incremental changes. There's no need to order incremental steps — you just diff two complete states.
- `from` clauses are structural, not versioned. They match on field names and types, not on "migration version 47."
- Fresh deployments (no snapshot) generate everything from scratch. No need to replay a history of migrations.
- The migration plan is computed, not stored. Two developers making different changes produce different migration plans — they don't conflict on a sequence number.

**What about rollback?** The previous snapshot is the rollback target. The compiler can diff current state against a previous snapshot to generate a reverse migration. This is computed on demand, not stored.

## Implementation

### Snapshot Format

Snapshots are serialized as a binary format (the same `.pluto` format used for AI-native representation):
- Schema declarations with all fields, types, conditions, `from` clauses
- Storage declarations with kinds, type bindings, indexes
- Enum declarations with variants
- Content-addressed for deduplication

### Compiler Changes

New compiler command: `plutoc migrate`

```bash
# Generate migration plan (dry run)
plutoc migrate --snapshot deployed.snapshot --dry-run

# Generate and save migration plan
plutoc migrate --snapshot deployed.snapshot -o migration-plan.sql

# Create a new snapshot from current source
plutoc snapshot -o current.snapshot

# Fresh deployment (no snapshot)
plutoc migrate --fresh -o init.sql
```

### Migration Planner

New compiler pass: `src/migration.rs`

1. Load snapshot (deserialize)
2. Load current schema/storage declarations from AST
3. Compute structural diff
4. Match `from` clauses to diff entries
5. Apply evolution rules (see `rfc-evolution-rules.md`)
6. Generate migration plan (ordered operations)
7. Determine single-phase vs two-phase
8. Output migration artifacts (SQL, deployment manifest)

### Integration with CI/CD

The migration plan is a build artifact. CI pipelines can:
1. Build the project
2. Generate migration plan against the production snapshot
3. Review the plan (automated checks + human review)
4. Apply the migration
5. Deploy the new code
6. Create a new snapshot

## Examples

### Example 1: Adding a Field

Source change:
```
schema User {
    id: string
    name: string
    email: string
    created_at: int from => timestamp()    // NEW: with default
}
```

Snapshot had: `id`, `name`, `email`.

Migration plan:
```sql
ALTER TABLE users ADD COLUMN created_at BIGINT DEFAULT extract(epoch from now());
```

Single-phase — backward compatible.

### Example 2: Renaming a Field

Source change:
```
schema User {
    id: string
    full_name: string from name: string => name    // RENAMED from "name"
    email: string
}
```

Migration plan (two-phase):
```sql
-- Phase 1: Expand
ALTER TABLE users ADD COLUMN full_name TEXT;
UPDATE users SET full_name = name;

-- Phase 2: Contract (after rollout)
ALTER TABLE users DROP COLUMN name;
```

### Example 3: Type Change with Transformation

Source change:
```
schema Product {
    id: string
    name: string
    price_cents: int from price: float => int(price * 100.0)    // CHANGED: float -> int
}
```

Migration plan (two-phase):
```sql
-- Phase 1: Expand
ALTER TABLE products ADD COLUMN price_cents INTEGER;
UPDATE products SET price_cents = CAST(price * 100 AS INTEGER);

-- Phase 2: Contract
ALTER TABLE products DROP COLUMN price;
```

### Example 4: Fresh Deployment

No snapshot provided:
```bash
plutoc migrate --fresh -o init.sql
```

Migration plan:
```sql
CREATE TABLE users (
    id TEXT PRIMARY KEY,
    full_name TEXT NOT NULL,
    email TEXT NOT NULL,
    created_at BIGINT NOT NULL
);
CREATE INDEX idx_users_email ON users (email);

CREATE TABLE products (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    price_cents INTEGER NOT NULL
);
```

## Open Questions

- [ ] **Snapshot storage.** Where do snapshots live? In the deployment registry? In a dedicated artifact store? In the repo (as binary files)? Recommendation: deployment artifact store, referenced by deployment ID.
- [ ] **Multiple snapshots.** Canary deployments have two versions running simultaneously. The migration plan targets the older snapshot. Should the compiler generate compatibility checks for both?
- [ ] **Data migration performance.** `UPDATE ... SET` on large tables is slow. Should the compiler generate batch/online migration scripts? Deferred — the plan format can be extended later.
- [ ] **Non-SQL backends.** Redis, DynamoDB, Kafka don't have DDL. Schema evolution for these backends means schema validation at read time (schema-on-read). How does this interact with the migration plan? The plan would include "update read schema" rather than "alter storage."
