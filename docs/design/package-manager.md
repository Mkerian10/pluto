# RFC: Pluto Package Manager

**Status:** Proposed (early design)
**Priority:** High (needed before external distribution)
**Related:** [build-cache.md](build-cache.md), [stdlib-embedding.md](stdlib-embedding.md)

## Problem

Today, Pluto has no way to use third-party libraries. The module system supports `import <name>` for local files and `import std.*` for the stdlib, but there's no mechanism to:

1. Declare dependencies on external packages
2. Fetch packages from a registry or URL
3. Version and resolve dependencies
4. Publish packages for others to use
5. Ensure reproducible builds across machines

## Prior Art

### Go Modules (decentralized + proxy)

- Packages identified by VCS URL: `github.com/foo/bar`
- No "publish" step — tag a commit, the proxy discovers it
- `GOPROXY` (proxy.golang.org) caches and mirrors modules transparently
- `go.sum` records SHA-256 checksums verified against a public checksum DB
- Immutable versions — once published, can't be changed
- Minimal Versions Selection (MVS) — uses the minimum version that satisfies all constraints

**Pros:** Simple, leverages existing Git infrastructure, no central authority needed
**Cons:** Need to run proxy/checksum infra, discoverability relies on documentation

### Zig (content-addressed, no registry)

- Dependencies declared in `build.zig.zon` with URL + hash
- The hash is the identity — URL is just "one of many possible mirrors"
- No version numbers in the protocol — just content hashes
- Global cache at `~/.cache/zig/p/{hash}/` — natural deduplication
- `zig fetch <url>` downloads and computes hash

**Pros:** Simplest possible design, immune to supply-chain attacks, no registry needed
**Cons:** No discoverability, no `zig search`, version management is manual

### Cargo (centralized registry)

- Central registry: crates.io
- `cargo publish` uploads packages
- `Cargo.lock` pins exact versions with checksums
- Semantic versioning with compatibility rules
- Rich metadata (categories, keywords, documentation links)

**Pros:** Great discoverability, rich ecosystem tooling
**Cons:** Central point of failure/control, supply-chain attack surface

### Deno (URL imports + JSR)

- Originally URL-based: `import from "https://deno.land/std/..."`
- JSR (JavaScript Registry): modern TypeScript-first registry
- npm compatibility via `npm:` prefix
- Multiple resolution strategies coexist

**Pros:** Flexible, progressive adoption
**Cons:** URL imports are fragile (server goes down = broken build)

## Proposed Design

### Design Principles

1. **Content-addressed** (from Zig) — The hash of the package content is the source of truth, not the name or URL
2. **Decentralized + discoverable** (from Go) — Packages are Git repos, but a proxy/registry aids discovery
3. **Reproducible** — Lock file with exact hashes, verifiable against a checksum DB
4. **Pluto-native** — Understands Pluto's module system, visibility rules, and type system

### Manifest File: `pluto.toml`

The `pluto.toml` file already exists for git dependencies (`plutoc update`). Extend it:

```toml
[package]
name = "my-app"
version = "0.1.0"

[dependencies]
# Git dependency (existing)
http-utils = { git = "https://github.com/pluto-lang/http-utils", tag = "v0.2.0" }

# Registry dependency (new)
json-schema = { version = "1.0" }

# URL dependency with hash (Zig-style, new)
crypto = { url = "https://packages.pluto-lang.org/crypto/v1.0.0.tar.gz", hash = "sha256:abc123..." }
```

### Lock File: `pluto.lock`

Generated by `plutoc mod fetch`. Contains exact resolved versions and content hashes:

```toml
[[package]]
name = "http-utils"
version = "0.2.0"
source = "git+https://github.com/pluto-lang/http-utils?tag=v0.2.0"
hash = "sha256:abc123..."

[[package]]
name = "json-schema"
version = "1.0.3"
source = "registry+https://packages.pluto-lang.org/json-schema/1.0.3.tar.gz"
hash = "sha256:def456..."
```

### CLI Commands

```
plutoc mod init                  # Create pluto.toml
plutoc mod add <package>         # Add a dependency
plutoc mod fetch                 # Download all dependencies, generate pluto.lock
plutoc mod update                # Update dependencies to latest compatible versions
plutoc mod why <package>         # Explain why a dependency is included
plutoc mod graph                 # Show dependency graph
```

### Local Cache

Content-addressed, shared across all projects:

```
~/.pluto/cache/
  packages/
    {content-hash}/         # Package source (deduplicated by content)
      pluto.toml
      src/
        main.pluto
        utils.pluto
```

### Resolution in `src/modules.rs`

When the compiler encounters `import http_utils`:

1. Check local files (existing behavior)
2. Check `pluto.toml` dependencies → resolve to cached package path
3. Check stdlib (embedded or filesystem)
4. Error: module not found

### Registry (Future)

A package registry at `packages.pluto-lang.org` with:

- **Proxy/mirror:** Caches Git-sourced packages for availability and speed
- **Checksum DB:** Merkle tree log (like Go's `sum.golang.org`) for integrity verification
- **Search API:** Package discovery by name, description, category
- **Documentation hosting:** Auto-generated docs from Pluto source

The registry is optional — Git URL dependencies work without it.

## Version Resolution

**Minimum Version Selection** (Go's approach):

Given constraints `A >= 1.2` and `A >= 1.3`, select `A = 1.3` (the minimum that satisfies all constraints). This is simpler than Cargo's SAT-solver approach, deterministic without a lock file, and avoids the "why did my dependency update?" surprise.

**Compatibility rules:**
- `1.x` → compatible with `1.0.0` through `1.x.y` (semver major)
- `= 1.2.3` → exact version pin
- `>= 1.2, < 2.0` → range constraint

## How Packages Map to Modules

A Pluto package is a directory with a `pluto.toml` and one or more `.pluto` files. When used as a dependency:

```toml
# Consumer's pluto.toml
[dependencies]
http-utils = { version = "1.0" }
```

```pluto
// Consumer's code
import http_utils

fn main() {
    let client = http_utils.Client { timeout: 5000 }
}
```

The package name in `pluto.toml` maps to the import name. The package's `pub` declarations are visible to the consumer. Non-`pub` items are private (existing visibility rules apply).

## Implementation Phases

### Phase 1: Git Dependencies (partially exists)

`plutoc update` already fetches git dependencies. Formalize:
- `pluto.toml` format for git dependencies
- `pluto.lock` generation with content hashes
- Integration with module resolver

### Phase 2: Local Path Dependencies

```toml
[dependencies]
shared-utils = { path = "../shared-utils" }
```

Useful for monorepos and local development.

### Phase 3: URL Dependencies (Zig-style)

```toml
[dependencies]
crypto = { url = "https://...", hash = "sha256:..." }
```

Content-addressed, no registry required.

### Phase 4: Registry

- Stand up `packages.pluto-lang.org`
- Implement proxy/checksum services
- Add `plutoc mod publish`

## Open Questions

- **Naming:** `plutoc mod` vs `plutoc pkg` vs `plutoc dep`?
- **Private registries:** Should we support private registries from day one? (Probably yes for enterprise adoption)
- **Monorepo support:** Can a single repo contain multiple packages? (Workspace concept like Cargo)
- **Binary dependencies:** Can packages depend on C libraries? How does that interact with the runtime linker?
- **Stdlib versioning:** Should stdlib versions be tied to compiler version, or independently versionable?
- **Diamond dependencies:** Two packages depend on different versions of the same library — how is this resolved?
