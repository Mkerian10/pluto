# RFC: Compiler-Side Package Management (`plutoc mod`)

> **Status:** Planning
> **Priority:** High — Blocks external distribution and ecosystem growth
> **Effort:** 4-5 weeks (phased)
> **Date:** February 2026

## Executive Summary

This RFC defines the phased implementation of package management within `plutoc` itself. The compiler owns the full dependency lifecycle: manifest parsing, dependency resolution, fetching, caching, lock file generation, and integrity verification. Registry integration (Nexus) is separate work — this RFC covers only what lives in the compiler.

**Objective:** Make `plutoc` a self-contained dependency manager (like `go mod`) so that third-party packages "just work" with `import <name>` using git URLs, path deps, and URL+hash archives.

---

## Background

### Current State

The compiler already has significant package infrastructure:

| Component | File | Status |
|-----------|------|--------|
| Manifest parsing (`pluto.toml`) | `src/manifest.rs` | Working — `[package]` + `[dependencies]` with path and git deps |
| Git dependency caching | `src/git_cache.rs` | Working — `~/.pluto/cache/git/{hash}/` with clone, checkout, update |
| Package graph resolution | `src/manifest.rs` | Working — transitive deps, cycle detection, diamond dep deduplication |
| Module resolution integration | `src/modules.rs` | Working — imports resolve against `PackageGraph` deps |
| Dependency name validation | `src/manifest.rs` | Working — identifier rules, reserved names (`std`, keywords) |
| `plutoc update` command | `src/main.rs` | Working — re-fetches all git dependencies |
| Integration tests | `tests/integration/manifest.rs` | 35+ tests covering path, git, transitive, error cases |

### What's Missing

| Gap | Why It Matters |
|-----|---------------|
| **Lock file (`pluto.lock`)** | Without pinned versions, builds aren't reproducible across machines |
| **Semver version resolution** | Git deps use rev/tag/branch but there's no version constraint solving |
| **Content integrity** | No verification that cached deps haven't been tampered with |
| **`plutoc mod` CLI commands** | No ergonomic commands for adding, removing, or inspecting deps |
| **URL+hash dependencies** | Only path and git supported; no tarball/archive deps |
| **Visibility enforcement for packages** | `pub` works but isn't enforced at package boundaries |
| **Dep-scoped stdlib** | Each dep should resolve `import std.X` independently |

### Design Principles

1. **Compiler owns the lifecycle** — `plutoc` handles fetch, resolve, cache, lock. No external tools needed.
2. **Go model** — Like `go mod`, the compiler is the package manager. A registry (like `pkg.go.dev`) is supplementary.
3. **Content-addressed** — Cache keyed by content hash, not by name or timestamp.
4. **Reproducible** — Lock file pins exact versions and content hashes. Same lock file = same build.
5. **Incremental** — Each phase builds on the last. The system is usable after every phase.

## Phase 1: Lock File Generation (1 week)

**Goal:** Make builds reproducible by recording exact dependency versions.

### Design

A `pluto.lock` file records the resolved state of all dependencies (direct and transitive):

```toml
# Auto-generated by plutoc. Do not edit.
# Run `plutoc mod update` to regenerate.

[[package]]
name = "mathlib"
source = "path:deps/mathlib"
hash = "sha256:a1b2c3d4..."

[[package]]
name = "strutils"
source = "git+https://github.com/pluto-lang/strutils?tag=v0.2.0"
rev = "abc123def456..."
hash = "sha256:e5f6a7b8..."

[[package]]
name = "logging"
source = "git+https://github.com/pluto-lang/logging"
rev = "789012abc..."
hash = "sha256:c9d0e1f2..."
```

### Fields

- **`name`** — Dependency name (matches `pluto.toml` key)
- **`source`** — Canonical source identifier (path, git URL + ref specifier)
- **`rev`** — For git deps: the exact commit SHA resolved at lock time
- **`hash`** — SHA-256 of the dependency's source tree content (all `.pluto` files, sorted)

### Content Hashing

Hash computation for a dependency directory:

```
hash = SHA256(
    for each .pluto file in sorted order:
        relative_path + "\0" + file_contents + "\0"
)
```

Only `.pluto` files are hashed — this means non-Pluto files (README, tests, etc.) don't invalidate the hash. The hash covers the source tree that the compiler actually consumes.

### Behavior

- **`plutoc compile`** — If `pluto.lock` exists, verify that cached deps match lock file hashes. If a dep is missing from cache, re-fetch it. If hash mismatches, error.
- **`plutoc update`** — Regenerate `pluto.lock` from current `pluto.toml`. Re-fetch git deps, recompute hashes.
- **No lock file** — If `pluto.lock` doesn't exist, resolve deps and generate it automatically on first compile. Print a notice.

### Tasks

1. Add `sha2` crate dependency for SHA-256 hashing
2. Implement `hash_directory(path) -> String` in `src/manifest.rs` — walks `.pluto` files, computes content hash
3. Implement `resolve_git_rev(dir) -> String` — runs `git rev-parse HEAD` in cached repo
4. Define `LockFile` struct with `Vec<LockEntry>` and TOML serialization
5. Implement `generate_lock_file(graph: &PackageGraph) -> LockFile`
6. Implement `verify_lock_file(lock: &LockFile, graph: &PackageGraph) -> Result<()>`
7. Integrate lock file generation into `find_and_resolve()` — write `pluto.lock` on first resolve, verify on subsequent
8. Add `--locked` flag to `plutoc compile/run/test` — fail if lock file is missing or out of date (for CI)
9. Tests: lock file generation, verification, hash mismatch detection, `--locked` enforcement

### Files Changed

- `src/manifest.rs` — Lock file types, generation, verification
- `src/git_cache.rs` — Add `rev_parse()` helper
- `src/main.rs` — `--locked` flag
- `Cargo.toml` — `sha2` dependency
- New: `src/lockfile.rs` (or inline in `manifest.rs` if small enough)

## Phase 2: `plutoc mod` CLI Subcommand Group (1 week)

**Goal:** Ergonomic CLI for managing dependencies.

### Commands

```
plutoc mod init                    # Create pluto.toml in current directory
plutoc mod add <name> --git <url>  # Add a git dependency
plutoc mod add <name> --path <p>   # Add a path dependency
plutoc mod remove <name>           # Remove a dependency
plutoc mod update [name]           # Update all or one dependency
plutoc mod list                    # List all resolved dependencies
plutoc mod why <name>              # Explain why a dependency is included
plutoc mod graph                   # Print dependency graph
```

### `plutoc mod init`

Creates a minimal `pluto.toml`:

```toml
[package]
name = "<directory-name>"
version = "0.1.0"

[dependencies]
```

### `plutoc mod add`

Adds a dependency to `pluto.toml` and immediately resolves it:

```bash
plutoc mod add strutils --git https://github.com/pluto-lang/strutils --tag v0.2.0
# Adds to pluto.toml:
# strutils = { git = "https://github.com/pluto-lang/strutils", tag = "v0.2.0" }
# Fetches, caches, regenerates pluto.lock
```

### `plutoc mod remove`

Removes from `pluto.toml` and regenerates `pluto.lock`. Does NOT remove from cache (cache is shared).

### `plutoc mod why`

Traces the dependency chain:

```
$ plutoc mod why logging
my-app -> strutils -> logging
```

### `plutoc mod graph`

Prints the full dependency tree:

```
$ plutoc mod graph
my-app v0.1.0
├── mathlib (path:deps/mathlib)
└── strutils (git:github.com/pluto-lang/strutils@v0.2.0)
    └── logging (git:github.com/pluto-lang/logging@abc123d)
```

### Migration: `plutoc update` -> `plutoc mod update`

The existing `plutoc update` command becomes an alias for `plutoc mod update`. Keep the old command working for backward compatibility but print a deprecation notice.

### Tasks

1. Add `Mod` variant to `Commands` enum with `ModCommands` subcommand group
2. Implement `mod_init()` — create `pluto.toml` from directory name
3. Implement `mod_add()` — parse args, modify `pluto.toml`, resolve, regenerate lock
4. Implement `mod_remove()` — remove from `pluto.toml`, regenerate lock
5. Implement `mod_list()` — pretty-print resolved graph
6. Implement `mod_why()` — BFS/DFS on `PackageGraph` to find dependency chain
7. Implement `mod_graph()` — tree-formatted output of full graph
8. Move `update` logic to use shared infrastructure, add deprecation notice
9. TOML writing: add `toml_edit` crate for in-place manifest modification (preserves comments/formatting)
10. Tests: each subcommand, edge cases (add duplicate, remove nonexistent, etc.)

### Files Changed

- `src/main.rs` — `Mod` subcommand group with `ModCommands` enum
- New: `src/mod_commands.rs` — Implementation of each `plutoc mod` command
- `src/manifest.rs` — `why()` and `graph()` queries on `PackageGraph`
- `Cargo.toml` — `toml_edit` dependency

## Phase 3: Version Resolution with Semver (2 weeks)

**Goal:** Support versioned dependencies with automatic resolution.

### New Dependency Syntax

Extend `pluto.toml` to support version constraints:

```toml
[dependencies]
# Existing (still works)
mathlib = { path = "deps/mathlib" }
strutils = { git = "https://github.com/pluto-lang/strutils", tag = "v0.2.0" }

# New: git + version constraint (resolves to matching tag)
json = { git = "https://github.com/pluto-lang/json", version = "1.0" }
```

### Version Constraint Syntax

Following Go's approach with semver:

| Constraint | Meaning |
|-----------|---------|
| `"1.0"` | `>= 1.0.0, < 2.0.0` (compatible range) |
| `"= 1.2.3"` | Exact version |
| `">= 1.2"` | At least 1.2.0 |
| `">= 1.2, < 1.5"` | Range |

### Resolution Algorithm: Minimum Version Selection (MVS)

Following Go's approach: given all version constraints across the dependency graph, select the **minimum version** that satisfies all of them.

**Why MVS over SAT-solving (Cargo)?**
- Deterministic without a lock file — same constraints always produce the same result
- Simpler implementation
- No "why did my dependency update?" surprises
- Lock file captures the exact result for reproducibility

### Git Tag Discovery

When `version = "1.0"` is specified with a git dependency:

1. Fetch all tags from the repo
2. Filter tags matching `v<semver>` pattern (e.g., `v1.0.0`, `v1.2.3`)
3. Apply version constraint to find matching versions
4. Select minimum satisfying version (MVS)
5. Record resolved version and commit SHA in `pluto.lock`

### Diamond Dependency Version Resolution

When two packages depend on different versions of the same dependency:

```
my-app
├── pkg-a (requires json >= 1.0)
└── pkg-b (requires json >= 1.2)
```

MVS resolves to `json 1.2.0` — the minimum version satisfying both constraints.

If constraints are incompatible (e.g., `= 1.0` and `= 2.0`), emit a clear error:

```
error: incompatible version constraints for 'json':
  pkg-a requires = 1.0.0
  pkg-b requires = 2.0.0
```

### TOML Changes

```rust
struct TomlDep {
    path: Option<String>,
    git: Option<String>,
    rev: Option<String>,
    tag: Option<String>,
    branch: Option<String>,
    version: Option<String>,  // NEW
}
```

### Tasks

1. Add `semver` crate dependency
2. Implement `VersionConstraint` type — parse constraint strings, check satisfaction
3. Implement `discover_git_tags(dir) -> Vec<(Version, String)>` — list semver tags + commit SHAs
4. Implement `resolve_version(constraint, available) -> Version` — MVS selection
5. Extend `validate_dep_spec()` to handle `version` field
6. Implement diamond resolution in `resolve_package_node()` — track version constraints, apply MVS
7. Update `pluto.lock` format to include resolved version
8. Update `plutoc mod add` to accept `--version` flag
9. Tests: version parsing, constraint satisfaction, MVS resolution, diamond deps, incompatible versions

### Files Changed

- `src/manifest.rs` — Version constraint parsing, MVS resolution, extended `TomlDep`
- `src/git_cache.rs` — Tag discovery, version-aware checkout
- `src/lockfile.rs` — Version field in lock entries
- `src/mod_commands.rs` — `--version` flag on `mod add`
- `Cargo.toml` — `semver` dependency

## Phase 4: Content Integrity & Verification (1 week)

**Goal:** Ensure dependencies haven't been tampered with between lock file generation and build time.

### Verification Flow

On every `plutoc compile/run/test`:

1. Read `pluto.lock`
2. For each locked dependency:
   a. Check cache for the dependency
   b. If cached: compute content hash, compare to lock file
   c. If not cached: fetch, compute hash, compare to lock file
   d. If hash mismatch: error with clear diagnostic
3. If no lock file: resolve and generate one (with notice)

### Strict Mode: `--locked`

For CI and reproducible builds:

```bash
plutoc compile main.pluto --locked
```

- Fails if `pluto.lock` is missing
- Fails if `pluto.lock` is out of date (doesn't match `pluto.toml`)
- Fails if any dependency hash doesn't match
- Never modifies `pluto.lock`

### Verification Mode: `--verify`

```bash
plutoc mod verify
```

- Recomputes all hashes and compares to lock file
- Reports any mismatches
- Useful for debugging supply-chain concerns

### Git Rev Pinning

For git dependencies, the lock file records the exact commit SHA. On subsequent builds:

1. Check that cached repo is at the pinned rev
2. If not (e.g., someone ran `plutoc mod update` without committing the lock), re-checkout the pinned rev
3. Verify content hash matches

### Tasks

1. Implement `verify_lock_integrity(lock: &LockFile, graph: &PackageGraph) -> Vec<IntegrityError>`
2. Implement `--locked` flag behavior in compile/run/test paths
3. Implement `plutoc mod verify` command
4. Integrate verification into the build pipeline (between manifest resolution and module resolution)
5. Add clear error messages: "dependency 'X' hash mismatch: expected abc123, got def456"
6. Tests: tampered dependency detection, missing lock file, stale lock file

### Files Changed

- `src/lockfile.rs` — Verification logic
- `src/manifest.rs` — Integration point for verification
- `src/main.rs` — `--locked` flag, `mod verify` command
- `src/lib.rs` — Wire verification into `compile_file()` path

## Phase 5: URL+Hash Dependencies (1 week)

**Goal:** Support tarball dependencies identified by URL and content hash (Zig model).

### Syntax

```toml
[dependencies]
crypto = { url = "https://packages.pluto-lang.org/crypto/v1.0.0.tar.gz", hash = "sha256:a1b2c3d4..." }
```

### Behavior

- Download archive to temp directory
- Compute SHA-256 of archive contents
- Verify against declared hash — if mismatch, hard error
- Extract to `~/.pluto/cache/url/{hash}/`
- The hash IS the identity — URL is just "one of many possible mirrors"

### `plutoc mod fetch-url`

Helper for discovering the hash:

```bash
$ plutoc mod fetch-url https://packages.pluto-lang.org/crypto/v1.0.0.tar.gz
sha256:a1b2c3d4e5f6...
```

Downloads, computes hash, prints it. User copies into `pluto.toml`.

### Cache Layout

```
~/.pluto/cache/
  git/           # Existing git cache
    {url-hash}/
  url/           # New URL cache
    {content-hash}/
      pluto.toml
      src/
        *.pluto
```

### Supported Formats

Start with `.tar.gz` only. Add `.zip` later if needed.

### Tasks

1. Add `flate2` + `tar` crate dependencies
2. Implement `download_archive(url) -> Vec<u8>` — HTTP GET with basic error handling
3. Implement `extract_archive(bytes, dest)` — extract tar.gz to directory
4. Implement `verify_archive_hash(bytes, expected_hash) -> Result<()>`
5. Extend `DepKind` enum with `Url(String, String)` variant
6. Extend `validate_dep_spec()` for url+hash deps
7. Implement `plutoc mod fetch-url` command
8. Integrate URL deps into `resolve_package_node()`
9. Tests: download + extract, hash verification, hash mismatch

### Files Changed

- New: `src/url_cache.rs` — Download, extract, verify, cache
- `src/manifest.rs` — URL dep handling in resolution
- `src/mod_commands.rs` — `fetch-url` command
- `Cargo.toml` — `flate2`, `tar`, HTTP client dependency

## Phase 6: Package Visibility Enforcement (1 week)

**Goal:** Enforce that packages can only access `pub` items from their dependencies.

### Current State

The `pub` keyword works for modules within a project, but package-level visibility isn't separately enforced. A dependency's non-`pub` items could theoretically leak through the flat namespace.

### Design

When flattening a package dependency's items into the consumer's namespace:

1. Only flatten items marked `pub`
2. Non-`pub` functions, classes, enums, traits, and errors are invisible to the consumer
3. Internal helper functions in a package stay private

### Implementation

In `src/modules.rs`, the `flatten_modules()` function already filters by `pub` for module imports. For package dependencies, apply the same filter at the package boundary.

### Transitive Visibility

Package A depends on Package B which depends on Package C. By default:
- A can see B's `pub` items
- A CANNOT see C's items (even `pub` ones) — must declare its own dependency on C
- B's internal use of C is an implementation detail

This matches Go's behavior: `import "B"` gives you B's exports, not B's dependencies' exports.

### Tasks

1. Audit `flatten_modules()` for package boundary visibility
2. Add package origin tracking to flattened items
3. Enforce transitive visibility rules
4. Clear error messages: "function 'foo' is not public in package 'bar'"
5. Tests: private items hidden, transitive deps not leaked, pub items accessible

### Files Changed

- `src/modules.rs` — Package-aware visibility filtering
- `src/manifest.rs` — Package origin metadata on `PackageNode`

## Migration Notes

### Backward Compatibility

All existing `pluto.toml` files continue to work. The only visible change is:
- A `pluto.lock` file appears next to `pluto.toml` on first compile
- `plutoc update` prints a deprecation notice suggesting `plutoc mod update`

### Lock File in Version Control

`pluto.lock` SHOULD be committed to version control for applications (reproducible builds). Libraries MAY omit it (consumers generate their own lock file).

### Cache Location

All caching continues to use `~/.pluto/cache/` (overridable via `PLUTO_CACHE_DIR`). No change to existing git cache layout.

## Future Work (Separate)

Registry integration (search, publish, shorthand `json = "1.0"` syntax) will be handled as a separate effort alongside the Nexus registry project. The compiler-side infrastructure from this RFC (lock files, semver, content hashing, URL deps) provides the foundation that registry integration will build on.

## Open Questions

- **Workspace support:** Should a single repo support multiple packages (like Cargo workspaces)? Probably a future phase if needed.
- **Binary/native dependencies:** Can a Pluto package depend on a C library? This interacts with the runtime linker and is probably out of scope for v1.
- **Stdlib as a package:** Should `std.*` modules eventually be publishable/versionable packages? For now, stdlib version is tied to compiler version.
- **Private git repos:** Authentication for private git repos (SSH keys, tokens). The git cache already delegates to system git, which handles auth natively.
